Engineering decisions

Safe retries

Issue and cancel endpoints accept an idempotency key. The same key and payload replay the original result; a changed payload returns a conflict.

Rules at two levels

A customer can have at most one active car policy. Service checks and a filtered unique SQL index both enforce that rule.

Concurrent changes

A row-version token detects stale policy updates, returning a conflict instead of silently replacing another change.

Traceable lifecycle

Issuing, updating and cancelling policies create audit events. Cancellation retains the record, and cancelled policies cannot be updated.

JWT-protected writes · rate limiting · xUnit testsPersonal project

Tests & contracts

xUnit endpoint tests cover conflicting idempotency keys, replay behavior, validation, JWT permissions and rate limits.

INSURANCE API / RELIABILITY

Making retries predictable

Why a repeated request needs a stable result.

A client can lose a response even when the server has completed a write. Retrying the request should not create another policy.

In my insurance API, issue and cancel operations accept an idempotency key. A matching key and payload replay the original result; a changed payload returns a conflict.

The implementation stores the operation, key, payload fingerprint and response entity ID. A unique constraint on operation and key prevents ambiguous reuse.
